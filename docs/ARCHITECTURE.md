# Architecture, Explainability and Creativity

## Pipeline
Visitor question (Persian/English) → external `data/semantic_model.md` and `data/schema.sql` → GapGPT Chat Completions planner → strict one-statement read-only SQL validator → `EXPLAIN QUERY PLAN` → SQLite authorizer and read-only connection → bounded rows → factual output + SQL + Trace.

No gold SQL from `eval_questions.json` is sent to the model or used to answer a visitor. The local dataset-integrity checker alone may read the reference queries to verify the supplied source data is intact; it never runs in the public application.

## Authority and error handling
- Allowed actions: `answer_from_query`, `ask_clarifying_question`, `refuse_write`, `refuse_out_of_scope`.
- LLM cannot change the database, read arbitrary files, browse external sports data, or assert unstored facts.
- SQL blocked before execution on write intent, multiple statements, forbidden SQL operations, unknown tables/columns/functions, invalid EXPLAIN, or timeout.
- SQLite read-only URI; container file permissions 0444; non-root container user; authorizer denies writes and unsafe functions; row limit 100 and time budget 2.5 seconds.
- Unclear questions trigger one follow-up; missing info triggers refusal rather than outside-world guesses.
- Row table, SQL, referenced tables and columns, validation, dry-run, row count, and timings appear in the UI.

## Independent semantic model
`data/semantic_model.md` maps goals, cards, own goals, penalties, lineups, coaches, referee decisions and home/away semantics to real schema. It is included at model-call time and can be refined independently of UI and code.

## Creativity
The interactive page makes the **SQL evidence inspectable** rather than hiding it: fans can inspect the exact read-only query, copy it, see the returned rows, and review the trace and safety checks in the same view. Suggested one-click questions help visitors explore the database while staying within the snapshot. No unverified statistics are generated by the presentation layer.

## Evaluation
`python scripts/evaluate_live.py https://<APP>.darkube.ir` submits all 17 supplied questions via public HTTP, then compares returned rows against expected rows. Trap questions require refusal without any database execution. The 15 source gold queries are NOT used in this live model run. Local `scripts/verify_dataset.py` is solely a database integrity check, not a model-accuracy score.

## Second-pass semantic review
When enabled, valid result rows and draft SQL are reviewed once by GapGPT for question/SQL alignment. A corrected candidate is never trusted automatically: it passes the same one-statement SQL validator, SQLite authorizer, EXPLAIN/dry-run, time budget, and read-only connection. The reference evaluator and expected rows are entirely absent from this production path. Review may increase latency and provider cost, and cannot guarantee semantic correctness; the 17-question public evaluation remains the acceptance test.


## Question-derived result contracts and normalization (v4)

`app/contract.py` derives grain, requested/default ranking size, label needs,
completion status checks and deterministic tie-breaking from the **user's
question**, not from evaluation cases. The response is evaluated against
actual returned SQLite rows and projected columns. Unresolved observable issues
can trigger two bounded model reviews, with candidates always revalidated.

`app/normalizer.py` is a conservative fallback for flat SELECT rankings: it
preserves model-produced WHERE/JOIN/GROUP BY and metrics, re-projects readable
labels and metrics, and orders ties consistently while applying a suitable
result limit. Every normalized SELECT goes through the same SQL allowlist,
SQLite read-only authorizer, EXPLAIN/dry-run, time and row budgets. It does not
read `eval_questions.json`, gold SQL or expected output rows. The API records
`result_normalization` and `semantic_warnings` for transparency.

This layer cannot fix faulty metrics/joins or certify any live test score.


## v4.2: Semantic cardinality checks and bounded FK projection

The validator can execute a syntactically safe but semantically misleading SELECT.
For team-scored goal rankings, `v_team_match` has one record for *each* side of
a match. Joining `goal` to this view on `match_id` alone may count a goal for
both sides. A question-derived diagnostic warns about the missing team-role
condition, and a conservative normalizer may append the documented
`goal.team_id = v_team_match.team_id` join constraint for a simple SELECT.
For other complex joins, the planner must repair the SQL itself.

For own-goal event lists, both scorer club (`goal.scorer_team_id`) and credited
club (`goal.team_id`) should be human readable. An independent check can
recognize omission of the scorer-club role. If the candidate already projects
the scorer, event and beneficiary, the normalizer may add a second `team`
foreign-key lookup to expose the missing role. It does not invent player names,
goal statistics or events.

All transformations are transparent in the returned SQL/trace, revalidated
through the same SQLite authorizer and read-only connection, and restricted
to non-destructive SELECTs. The live planner never receives evaluation
questions' reference SQL or expected result rows.
